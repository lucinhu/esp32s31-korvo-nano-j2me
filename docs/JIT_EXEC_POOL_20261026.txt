已经落实的改动
1. 可执行内存：默认选择单独映射的 512 KiB 代码池，避免与驱动抢占原有内部可执行堆。按缓存行独立分配，分配表与机器码分开；提交时完成数据写回、指令失效和同步。每次创建池会验证同地址返回 42、改写后返回 43，退出后解除映射并释放全部内存。初始化失败会回退解释执行。
2. 方法查找：方法切换使用哈希索引，回收槽位时维护冲突链，避免遍历整个方法表。
3. 扩大容量时修复位宽：代码槽保存十位索引，方法映射偏移和已用空间使用 32 位；防止槽号超过 255、状态空间超过 65536 个单元后截断。上游原有默认容量保持不变。
4. 本工程配置：1024 个代码槽、4 路关联、1024 个方法记录、256 KiB 状态空间；普通块至少 8 条字节码，有预算限制的循环可单独编译。代码池、VM 元数据及分配表约占 512 + 383 + 16 KiB，游戏的实际内存余量需要一起考虑。
5. 增加菜单串口命令 jit memory mapped/internal，支持同一固件切换执行内存；保留 jit on/off/probe。测量工具记录池回收、提交耗时、代码哈希和音频增量。

蹦球旧内部执行路径的本轮基线为 11.165 FPS，最终开启为 15.355，约提高 37.5%；但关闭时仍有 16.155，不能声称开启 JIT 已稳定胜过解释器。中间较大缓存配置的重复值为 14.765—16.780，也反映了短场景的波动。两款游戏的最终前后截图已核对，处于真实关卡/驾驶画面。
热力追踪属于功能验证，导航受时序影响进入的驾驶场景与历史测试不同，不与历史数值比较。
FPS 是实际改变画面的采样值，非 VM 调度帧率或屏幕刷新率。每组预热 5 秒，蹦球/亡命狂飙采样 20 次，热力追踪 10 次；采样期间不截图。相同输入流程不等于逐帧状态完全相同，以上不是全游戏平均帧率或统计显著性结论。

容量实验与剩余瓶颈
只更换映射后，蹦球整轮方法映射淘汰 167043 次、代码编译 24096 次；最终分别为 0 次、640 次，代码淘汰 51 次。最终亡命狂飙方法映射淘汰也是 0，仍有 1577 次代码淘汰。
早期中等容量配置会让赛车更慢，因此不能只增加任意一个缓存就认为有效。本轮最终设置恢复了大部分旧 JIT 的 2D 帧率损失，但赛车仍以解释模式更快。后续应测量每块的净收益与解释/原生切换成本，再做选择性编译、较长热点区域和栈值保留；当前日志没有把这些成本逐项计时，不把它们当作已测定的唯一原因。
