# nano_j2me RV32 JIT 修改建议

后续更新：上游 `fe974fc` 已实现探测/执行拆分、最小块长度、两路缓存及 RV32 块内寄存器缓存等改动。旧版分析和数据保留在下文；新版本板上对照、纯内核与当前建议见 [LATEST_3D.md](LATEST_3D.md)，不要将下文的缺失功能当作最新版本状态。

针对上游 `fed8d0c3d2e42560c9bc33dba3288989412e043f`。本文基于 ESP32-S31-Korvo-1 的源码检查、测试 JAR 反汇编和板上计数，**没有修改 nano_j2me 源码，也没有向上游发布 issue/PR**。完整数据见 [jit-results.json](jit-results.json)，复现步骤见 [UPSTREAM_GAMES.md](UPSTREAM_GAMES.md)。

## 已经确认的事实

CPU 320 MHz，PSRAM 250 MHz，240×320，音量 40，FPS 叠加关闭。同一固件通过公开 JIT API 在每次 VM 创建后启用/关闭，使用同一 JAR 和全新 RMS；融合指令在两组均关闭。解释器及 JIT 分发均已放入内部 IRAM，生成代码也在内部 SRAM。代码提交使用 `fence.i`，所有代码内存申请成功，排除了“根本没执行”和“反复申请失败”作为最终数据的解释。

| 项目 | JIT 关闭 | JIT 开启 |
| --- | ---: | ---: |
| 固定计算两轮平均耗时 | 9.7966 s | 14.7888 s |
| 每轮固定计算量 | 120×4000 | 120×4000 |
| 计算校验值 | -1082513742 | -1082513742 |
| 第1轮 VM 调度帧 | 313 | 553 |
| 第1轮 LCD 实际更新 | 240 | 242 |
| 第1轮画面提交累计耗时 | 2.0507 s | 2.8916 s |
| 第1轮执行 Java 指令 | 11,385,053 | 11,390,671 |

CPU **端到端耗时增加 51.0%**，包含加载、调度、绘图和销毁，不是隔离后的纯算术时钟数。新增显示提交成本约 0.84 s，也解释了一部分差距；不能将全部 5 s 都归到某一个 JIT 函数上。VM 报告的 FPS 反而从 32.1 升至 37.5，因为调度帧数也增加了；它不能证明游戏变快。两组最终画面 CRC 一致，实际更新次数相近。

每轮 CPU：`compiled=2241 executed=3920966 bytecodes=6460115`。原生块平均仅 **1.6476 条 Java 指令/次**。JIT 代码分配峰值 976 B、分配拒绝 0、退出全部释放。解释器最终同样使用 CPU 的乘法等硬件指令，JIT 的收益主要来自减少字节码调度和槽访存，不会让相同的乘法指令本身变得更快。极品飞车16 的启动场景编译 20,340 个块、执行 697,340 次，64 槽直接映射缓存发生大量替换，但现有统计不能区分唯一热点与同一热点的重复编译。

## 为什么目前很难摊薄成本

[每次取指前的 JIT 探测](https://github.com/lucinhu/nano_j2me/blob/fed8d0c3d2e42560c9bc33dba3288989412e043f/src/core/nj_interp.c#L1413-L1430) 会先 `SAVE()`，即使该位置未变热、不支持或缓存未命中。`SAVE()` 写回 PC/SP 并刷新累计字节码计数。命中后还有缓存检查、栈上下界/调度额度检查、函数调用及统计更新；对于约 1–2 条 Java 指令的小块，这些工作可能比省下的解释器分发更多。

[编码器遇到不支持指令就终止直线块](https://github.com/lucinhu/nano_j2me/blob/fed8d0c3d2e42560c9bc33dba3288989412e043f/src/core/nj_jit_rv32.c#L482-L513)。实际上传的 `PerfBench$Screen.run()` 内循环有：

```text
22: getfield checksum
25: ldc 1664525
27: imul
28: ldc 1013904223
30: iadd
31: putfield checksum
...
43: bipush 13
45: iushr
46: ixor
47: putfield checksum
50: iinc
53: goto 12
```

当前 `ldc`、字段访问、分支、数组和方法调用都留在解释器，导致乘加和循环被切成很多小块。生成代码也基本仍在读写 Java 栈槽，没有跨指令的栈顶寄存器缓存。以上是源码支持的开销来源；**各项准确占比仍需增加目标板周期剖析来确定**。

## 建议优先做的改动

### 1. 把无副作用的探测与需要 SAVE 的路径分开

在解释器快速路径先检查是否是候选起点、是否冷却或已确定不支持，未命中就直接继续解释。候选信息可以使用热点方法的 PC 位图，或独立于易冲突代码缓存的负缓存。

只移动无分配、无回调、无 Java 执行的探测。编译、可执行内存回调及任何可能分配/GC/重入的操作前仍须保存精确 PC/SP；保留当前安全契约，不能直接删除 `SAVE()`。先测“JIT 已安装但不执行块”相对解释器的额外周期，再测命中路径。

### 2. 给编译和执行增加收益门槛

当前只要块包含一条支持指令就可能编译。增加可配置的 `NJ_JIT_MIN_BLOCK_INSNS`，例如将 4/8 作为实验点，并结合热度和发射的访存指令数量判断收益。太短的 `aload`、单个算术、`iinc` 块留给解释器。

门槛应在反复发射/分配之前判断，并和第1项一起验证；仅拒绝短块而保留每次昂贵探测，仍可能变慢。比较阈值时固定 JAR、工作量和输入，检查是否减少总运行时间，而非只增加原生执行比例。

### 3. 先补基本类型 ldc，再扩展能形成循环的覆盖

首先支持 `ldc/ldc_w` 的 int/float 常量，做常量折叠，使示例中的乘加至少能进入更长的同一块。String、Class 常量的加载/分配与初始化行为继续回退，不能按普通立即数处理。

之后考虑已解析字段偏移的 `getfield/putfield`，以及整数比较/条件跳转/回边。字段访问要保持空指针异常位置、类初始化/解析、引用存储和 GC 契约。编译循环超出现有叶子直线块契约，回边必须扣减调度额度并保留退出/调度点，不能用一个不返回的本机循环阻塞其他 Java 线程或输入。

### 4. 在一个块内部缓存栈顶和临时值

在 caller-saved 寄存器中保留 1–2 个栈顶值，做相邻 load/store 消除、常量传播和简单寄存器分配，减少每条 Java 指令对 8 字节槽的访存。先限制在当前无调用、无分配的叶子块内。

在所有退出路径完整写回脏槽，保持高半部、宽值上层槽清零规则和引用根可见性。复用上游完整槽字节对照测试，增加极值、别名局部变量、除零、NaN 及量子耗尽测试。

### 5. 改缓存策略，并先补能解释结果的计数

[现有缓存](https://github.com/lucinhu/nano_j2me/blob/fed8d0c3d2e42560c9bc33dba3288989412e043f/src/core/nj_jit.c#L142-L157) 按 `(method, pc)` 哈希到 64 个直接映射槽，不同热点会互相驱逐，驱逐也丢失热度/拒绝信息。建议试 2/4 路组相联，或热点方法内的 PC 映射；将负缓存与机器码缓存分开。128/256 槽可作为 A/B 参数，但应报告元数据和代码内存成本，不直接无限扩大。

建议新增：查询/命中/驱逐/同一站点重编译次数，失败原因（不支持、太短、预算、内存）、按实际执行次数加权的块长分布、编译与执行周期、原生字节码占比。RV32 每块的多个 64 位计数也有成本，可以提供可关闭或按调度批量刷新的统计模式，同时规定公开统计 API 的可见边界。

## 最小验证矩阵

至少分别测：纯局部变量算术、大常量乘加、字段累加、数组循环、分支循环，以及游戏实际场景。这样能分清“后端生成代码慢”和“覆盖不足、探测/调度成本高”。加入 JIT 关闭、开启但拒绝执行、正常开启三组；性能计数可再分详细统计开/关。

首先验证校验值、完整栈槽、异常 PC、调度公平性和内存回收，再比较固定工作量耗时及实际画面更新 FPS。测试包含 240×320 显示和音频并发；WAV/MIDI 播放完成、源样本完整接收、欠载次数也纳入回归。不要用调度帧 FPS 单独判断加速，不预先承诺某个修改能获得特定倍数。
