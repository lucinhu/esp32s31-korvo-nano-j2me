# c6b1595 实机测试（匿名目标）

2026-10-23，核心固定为 `c6b1595c083044844979db4d0fb2f0fdf1d9f664`，子模块源码保持原样。只烧录应用，保留已有游戏和正常存档。测试固定 240×320、音量 40，融合指令和 threaded dispatch 关闭，JIT 普通统计开启、详细统计关闭；每次 `bench` 使用新建临时 RMS，结束后清理。

结论：**新版 JIT 已明显改善计算性能，但实测游戏收益仍不稳定：两款 3D 场景没有明显收益，2D 蹦球传说开启后更慢，涂鸦地带单轮均值略高但中位数相同，复杂启动场景仍有减速，因此保持运行时默认关闭。** 按游戏试用串口 `jit on`；纯内核的收益不能直接换算成游戏帧率。

原始数值经过匿名化后保存在 [jit-c6b1595-results.json](jit-c6b1595-results.json)。旧版结果仍在 [LATEST_3D.md](LATEST_3D.md)，不要混用版本。以下结论仅来自本轮测量，不代表所有游戏、关卡和整个运行流程。

## 纯计算内核

五内核继续使用上轮嵌入的相同 JAR，哈希在 JSON 中；新增 mixed 使用上游原始 `JitPerf.mixed`，通过单独的 3474 B 测试 JAR 上传。没有修改上游计算方法。mixed 的 `553f49c9` 校验值同时由独立 Python 32 位运算参考和桌面 JVM 验证。

每项 50,000 次迭代、每种模式两个新 VM，表中为毫秒均值。每个内核先用零迭代完成初始化；同一个五内核夹具中，各项按顺序运行。计时排除显示、音频和打印，包含对应 JIT 热身/编译。结束后才创建空白 Canvas、验证正常退出。计时分辨率为毫秒，重复次数仅两次，倍数是观察值。

## 端到端固定工作量

同一固件，仅切换运行模式。CPU 与重绘各两轮平均，音频和两个赛车启动各一轮；FPS 叠加关闭。包含加载、显示、调度及销毁，不是纯计算耗时。

| 项目 | JIT 关闭 | JIT 开启 | 开启后耗时变化 |
| --- | ---: | ---: | ---: |
| CPU，120×4000 | 8.6015 s | 7.8880 s | -8.3% |
| 240 次完整重绘 | 5.4501 s | 5.4532 s | 约不变 |
| WAV + MIDI 夹具 | 10.6611 s | 10.5472 s | -1.1% |
| 极品飞车14，300 VM 帧启动 | 7.2415 s | 7.3363 s | +1.3% |
| 极品飞车16，300 VM 帧启动 | 11.4964 s | 13.8676 s | +20.6% |

固定测试每项两组的最终游戏原始画面及 LCD 区域 CRC 相同，CPU 校验值保持 `-1082513742`。这些赛车数据只覆盖启动，不能代表赛道 FPS。

CPU 第 1 轮开启 JIT：编译 14 个块、执行 527072 次、原生执行 8406361 条 Java 指令，平均每次约 15.95 条，约占整轮 Java 指令的 73.8%；代码驱逐和分配/提交失败均为零。旧版相应约为 4.08 条/次、18.9%，新字段及长块/循环路径确实在实际设备上执行。

与旧版相比，新版解释器及 JIT 端到端都改善；本次更新还包含类缓存、图形、流和光栅化优化，不能把跨版本的全部改善只归因于 JIT。

## 2D 重绘与真实场景 FPS

相同 240 次完整重绘夹具、相同最终原始画面及 LCD CRC：旧版 `fe974fc` 关闭 JIT 两轮平均 8.066562 秒，新版关闭 5.450121 秒，耗时减少 **32.4%**。这是固定工作量的跨版本改善，包含加载和销毁，不能直接说成游戏 FPS 提升 32.4%。新版同固件开关 JIT 则为 5.450121 / 5.453170 秒，约不变。

另外进入两款 2D 游戏的初始关卡，检查前后 240×320 原始游戏截图。导航后预热 5 秒，轮流点按数字 6、4，使角色在初始区域左右行走；持续按住方向键仅产生很少移动，因此改用点按。每个脉冲请求按下/松开各 0.25 秒，受串口和 VM 响应时间影响，实际间隔更长；记录了实际脉冲数及采样时间。两种模式使用相同导航和输入规则，采样期间无截图，FPS 叠加开启。每种模式只测一轮，40 个读数、请求间隔 0.55 秒，实际窗口约 25–26 秒。

| 场景 | JIT 关闭均值 | JIT 开启均值 | 中位数（关/开） | 范围（关/开） |
| --- | ---: | ---: | ---: | --- |
| 蹦球传说，第一关初始平台左右点按 | 15.33 | 10.62 | 15.60 / 11.25 | 9.6–19.4 / 5.9–13.9 |
| 涂鸦地带，初始区域左右点按 | 3.34 | 3.79 | 3.90 / 3.90 | 0–7.8 / 1.9–7.8 |

蹦球这一轮开启后均值低约 30.8%，两组含预热均为 37 次点按。涂鸦均值高约 13.2%，但中位数相同，含预热点按数为 37 / 38；计数窗口、输入相位和动画节奏都影响读数，不能据此确认稳定加速。这些数字描述指定操作下实际变化画面的速率，不代表最高绘制能力或整款游戏的平均帧率，也没有与旧版同关卡配对，不能推断跨版本游戏 FPS 的幅度。

蹦球开启组整轮（含启动和导航）编译 20228 个块、代码驱逐 20164 次、方法映射驱逐 65134 次，分配/提交失败及 faults 为零。大量驱逐值得优先分析，但没有周期剖析，尚不能把减速精确归因给某一项。两款游戏均正常退出、内存回收且缩放检查通过；涂鸦日志中仍有缺失资源等兼容性异常。

最初的 1945 片头、蹦球菜单采样已排除；蹦球开场对话/持续按键及涂鸦持续按键的诊断结果单独归档，不混入上述行走对照。特别是开场动画曾出现不同方向的均值变化，说明场景和操作一致性十分重要。

## 真实 3D 场景 FPS

通过脚本进入相应场景，并检查前后 LCD 截图。预热 5 秒后每秒读取一次已有 `fps` 诊断，共 20 次；采样期间无截图。FPS 叠加开启，统计实际变化画面数，不是 LCD 扫描或 VM 调度帧率。均值是 20 个约半秒窗口读数的平均，不是整段累计帧数的精确平均。每种场景仅一轮，导航和同类操作一致，未保证两组处于逐帧相同的敌人/相机状态，因此不把小幅差异当作稳定回归。

| 场景 | JIT 关闭均值 | JIT 开启均值 | 中位数（关/开） | 范围（关/开） |
| --- | ---: | ---: | ---: | --- |
| 鬼泣3D，第一关敌人同屏，保持 FIRE | 9.98 | 9.71 | 9.65 / 9.40 | 9.2–12.1 / 8.9–11.0 |

摩托两组各有短暂无更新窗口，保留了零读数，没有删去低值。鬼泣首次尝试停在关卡开始提示，所得全零读数已排除；增加关卡加载等待后，前后画面确认实际战斗，再记录表中结果。

两种 3D 后端都实际绘制了三角形。JIT 开启组执行了生成代码，退出均 `rc=0`，内存与缩放检查通过。此处建立的是初期操作/渲染可运行，未验证通关和所有攻击判定。

## 音频与兼容性边界

独立音频夹具两种模式均完整播放 WAV 3.000000 秒、MIDI 3.139682 秒。接收 135380 源 PCM 帧、codec 总输出 297472 个立体声帧，驱动错误及欠载为零；总输出含正常补静音。各有一次首包部分接收，运行器重试余下数据，未据此判定丢帧。没有人工听音或麦克风评价。

3D FPS 的无截图采样窗口也记录了音频差分，但四个窗口都没有新增源 PCM 接收，因此不能用其零欠载来证明持续有声实战音频正常。截图暂停带来的累计欠载与独立夹具结果分开保存。

2D 蹦球左右点按的采样窗口确有源 PCM 接收：关闭/开启组分别接收 493320 / 482312 帧，输出 1079808 / 1055232 个立体声帧（含少量补静音），窗口内新增驱动错误和欠载均为零。整轮累计欠载均为 1，包含采样前截图等暂停，不能与窗口差分混为一谈；这些计数仍不替代听音评价，也没有建立音频开关的性能对照。涂鸦窗口没有新增音频。

六款额外游戏各进行 JIT 开/关 300 VM 帧按键采样：俄罗斯方块、贪吃蛇、涂鸦地带、1945空战英雄、钻石狂潮、蹦球传说，均正常退出并回收内存。部分游戏捕获了 Vector 空元素、缺失图像或首次 RMS 缺失等异常；`rc=0` 不代表所有内容正确或可以完整游玩。

**待核对项：钻石狂潮的末帧 CRC 在两种模式下不同。** 追加两轮/模式后，关闭组均为 `e9fe5d31`，开启组均为 `297038d9`，LCD 对照也分别稳定；差异可以复现。相同 VM 帧输入脚本尚未固定游戏时钟、随机种子和线程/输入所处状态，不能只凭 CRC 判定 JIT 语义错误，也不能宣称像素一致。此项作为兼容性差异保留，后续应对齐逻辑状态后追踪。

复现该采样：240×320、音量 40、FPS 关闭、新 RMS，300 VM 帧，按键 `30:fire,60:soft1,100:5,160:fire,200:right:down,260:right:up`。

## 建议与最终状态

保留运行时默认 JIT 关闭，允许按应用手动试用。新版本已经落实字段、整数数组、分支、受调度预算限制的循环及方法内探测映射，旧建议不再将其列为缺失功能。

后续优先测复杂场景的缓存和方法映射成本：极品飞车16 启动有 5668 次代码驱逐、22938 次方法映射驱逐；鬼泣探索运行有 16331 次代码驱逐、50363 次方法映射驱逐。代码分配/提交均无失败，不能把这些现象解释为可执行 RAM 申请失败。驱逐计数不能直接量化耗时，建议增加编译/查表/执行及原生图形函数的周期剖析，再独立比较映射容量和热点方法选择。

2D 蹦球也复现了大量驱逐。当前默认代码缓存为 64 项、2 路，每组轮流替换；方法状态表为 32 项、4096 B arena（见 `nj_config.h` 和 `nj_jit.c`）。建议分别测试缓存项数、相联度、替换策略和方法映射容量，记录命中率、实际代码字节、元数据及各阶段耗时，区分冲突驱逐、容量压力和低收益编译。不要只增加可执行字节预算：当前样本没有申请失败。以上为后续实验建议，本轮未修改核心或调整容量参数。

3D 图形工作由本机 C 后端承担，Java JIT 不直接优化该部分；本轮没有完整热点周期分布，不指定其为唯一瓶颈。

最后完成三轮 JIT 开启、三轮关闭的内置演示启停，另用独立临时 RMS 检查按键和指针输入，全部正常退出且内存恢复。主机的三项 JIT 接口/编码器检查已通过。补充 2D 测试后再次查询，设备留在菜单：240×320、音量 40、JIT 关闭、FPS 开启，现有游戏和正常存档保留。

新增混合夹具自身占用 4096 B 文件系统空间。补充 2D 之前/之后 FAT 可用空间为 393216 / 380928 B，各轮临时 RMS 均返回清理成功；额外 12288 B 的占用变化尚未定位，不能据此宣称测试前后存储占用完全一致。游戏列表仍为 23 项，正常 RMS 路径未用于这些测试。
