# 2D 游戏性能与 GameCanvas 提交优化（2026-11-11）

本轮以《鲁宾逊漂流记汉化版_702.jar》和《合金弹头4(完美汉化版)_4053.jar》为实机样本。保留原始 JAR、正常 RMS 和 240×320 / MAX SIZE 配置。串口为 `/dev/ttyUSB1`，只烧录应用区。原始数据见 [本轮记录](updates/2026-11-11-2d-opt)。

## 已实施的核心与板级修改

为 `nj_port` 追加可选的 `display_idle` 回调。当前 GameCanvas 已经使用 `flushGraphics()` 主动提交后，如果本次调度没有提交或绘制，且没有活动的视频覆盖，核心通知宿主画面空闲。ESP32 此时只维护 FPS 浮层，不再读取、比较整张 RGB565 帧缓冲。未设置回调的平台保留原有逐调度帧的 `display_present` 行为。

这依赖的是“已经提交的屏幕保持不变”，并不假定游戏的离屏绘图缓冲没有变化。缓冲仍可能正在画下一张地图。优化没有重新引入超时补画，也没有让按键或触摸复制正在绘制的缓冲。有效的完整/局部 flush、显式 repaint、画布切换及视频覆盖仍进入原有提交路径。普通 Canvas 和没有主动 flush 的旧 GameCanvas 保留既有兼容行为。

这遵循 [Oracle GameCanvas 文档](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/lcdui/game/GameCanvas.html) 对离屏绘制、flush 后可立即绘制下一帧、局部刷新和隐藏画布的约定。旧的闪烁成因见 [鲁宾逊修复记录](ROBINSON.md)。

`KORVO_GAMECANVAS_IDLE` 默认开启；可用 `-DKORVO_GAMECANVAS_IDLE=OFF` 构建对照版本。它不影响 LCD 的缓冲所有权、同步等待或 DMA2D 脏区同步。

## 测量方法与边界

游戏实际画面更新 FPS 与 VM 调度次数分开报告。静止菜单可能为 0 FPS；高频重复提交也不代表游戏跑得快。旧记录 `robinson-before.json`、`robinson-baseline.json` 和 `robinson-map-before.json` 包含菜单、加载或开场说明页，不能用作地图走动的前后性能对比。

新增 `STATUS updated/unchanged/idle` 计数；`measure_scene_fps.py --counter-fps` 可关闭 FPS 浮层，根据实际更新计数和墙钟时间测量。采样期间不截图，截图仅用于确认场景。浮层法与计数法应分别比较，避免混用。

通过 `javap -c -p` 检查这两份原始 JAR：鲁宾逊 `data.k` 构造器把默认帧间隔设为 60 ms，循环扣除本帧工作时间后等待；游戏也有修改该间隔的入口，因此不能据此断言所有场景都固定为 16.7 FPS。合金弹头4的 `run()` 以 40 ms 计算下一次更新的等待，名义目标为 25 FPS。运行效率应与各自的游戏循环和实际场景一起判断。

固定工作量夹具 `FramePipelineBench` 每个阶段完成 48 次绘制与不同数量的 Java 计算。比较耗时，同时检查 paint 数量、计算校验值、原始屏幕与缩放后 LCD CRC；不把重复调度计入工作量提升。

该夹具使用普通 Canvas，作为本轮的无关路径回归对照：两个新 VM 的平均耗时如下。不能把毫秒级波动解释为 GameCanvas 优化的收益。

| 每帧计算迭代 | 原来 / ms | 优化后 / ms |
| --- | ---: | ---: |
| 0 | 1323.5 | 1324.0 |
| 2000 | 2449.0 | 2448.0 |
| 6000 | 4873.5 | 4855.5 |
| 12000 | 9070.5 | 9038.0 |

每阶段均为 48 次 paint，计算校验值相同，最终原始屏幕 CRC `e6a32b6b`、LCD CRC 也一致。原始数据为 `pipeline-before/after.json`。

同一最终固件的 JIT 开关对照，每个内核 50,000 次迭代、两个新 VM 的均值：

| 计算内核 | 解释器 / ms | JIT / ms |
| --- | ---: | ---: |
| 局部变量 | 145.0 | 9.0 |
| 常量 | 113.5 | 4.5 |
| 字段 | 225.5 | 10.0 |
| 数组 | 207.5 | 18.0 |
| 分支 | 205.5 | 9.5 |

校验值均匹配。整个夹具（包含显示、加载、退出）的耗时约 1.191→0.349 s，不能用内核约 17.5 倍的合计差异代替端到端约 3.4 倍。JIT 每轮只编译 5 块，机器码峰值约 1502 B，没有代码/方法映射驱逐和执行故障。解释器该负载约 4.24 M 字节码/秒；算术上每 33.3 ms 约 14 万条，尚未计入真实游戏额外的原生绘图、显示及调度成本。这是特定计算负载的测量，不是所有 Java opcode 的统一吞吐量。

## 防闪烁验证

核心回归在公共 Display / Graphics / GameCanvas API 上操作，覆盖：

- 下一帧只完成上半部分，跨越 310 次调度仍保留上一张完整图像。
- 按键、触摸与隐藏画布 flush 不提前公开离屏像素。
- 局部 flush 只更新指定区域；之后逐字节验证整张已提交画面保持一致。
- 显式 repaint、serviceRepaints、画布切换、旧 GameCanvas 和未启用新回调的平台。
- 在主动提交的 GameCanvas 上播放真实 MPEG-4 视频时，视频仍走正常显示提交；停止后恢复 idle 通知。

完整结果在 `fullscreen-tests.log`。另有 Java 分段绘图夹具：交替逐像素绘制红/蓝色，故意在中途睡眠，检查提交画面是否混有两帧颜色。截图只能验证采样时刻；核心逐字节回归补足截图之间的观察空隙。

设备游戏分区剩余 253952 B，低于上传工具要求保留的 262144 B，因此没有删除旧游戏或降低存档预留。最终应用通过现有 `KORVO_DIAGNOSTIC_JAR` 配置内置 `tests/fixtures/flushdemo.jar`，额外约 2.5 KiB 应用空间，不占游戏分区；菜单诊断项的标题改为通用 `Diagnostic MIDlet [APP]`。实机复现工具为 `tools/verify_gamecanvas_commits.py --embedded`，它在方向键和触摸交错期间采样整张 240×320 已提交屏幕，并进行 90 次 LCD 缓冲一致性检查。构建记录在 `diagnostic-build.log`；主逻辑与游戏测试固件相同，新增的只有诊断 JAR 及其菜单标签。

最终验证：核心防半帧回归 **16269 项检查、0 失败**，相关 14 项宿主 ASan/UBSan 测试和 4 项适配测试通过。实机 8 张采样均为完整单色，90 次 LCD 检查 `mismatches=0`，显示同步 `timeouts=0`；预热后退出 PSRAM `delta=0`。首次冷启动的夹具运行曾多保留 532 B 宿主分配，工具先运行一帧内置演示预热后再检查回收，未将冷启动分配直接认定为夹具泄漏。新 `--counter-fps` 路径也通过实机检查，三次样本均使用 updated 计数且没有 FPS 浮层。

最终固件 8276608 B，SHA-256 `3d06aa9e4fee22f1b18390e7c26a4301f9378c684c0f3d6ded9000e11926d2a1`，应用烧录已校验。退出后留在菜单，240×320、MAX SIZE、音量 40、JIT 关闭、FPS 关闭；游戏和正常存档保留。核心修改提交为 `c6c618e`，板级适配和实测记录与本报告一同提交；本轮汇总见 `summary.json`，测试输出见 [validation.txt](updates/2026-11-11-2d-opt/validation.txt)。

## 鲁宾逊地图实测

同为 240×320、MAX SIZE、JIT 关闭、临时 RMS，进入地图后预热 3 秒，采样 16 次，按 2 秒周期轮流点按 6/8/4/2；采样期间无截图。前后地图截图已检查。该一轮对照的结果：

| 指标 | 设备原固件 | 启用 idle 回调 |
| --- | ---: | ---: |
| 变化画面 FPS 均值 | 3.631 | 4.738 |
| FPS 中位数 | 3.9 | 3.9 |
| FPS 读数范围 | 1.9–3.9 | 3.9–5.9 |
| 整轮显示提交累计耗时 | 44.042 s | 3.436 s |
| 整轮显示提交占墙钟时间 | 40.43% | 3.15% |
| 整轮宿主显示回调次数 | 13772 | 621 |
| 空闲通知次数 | 未实现 | 1454987 |

均值观察提升约 30.5%，中位数没有提高。只有一轮配对，输入相位、动物动画和半秒 FPS 窗口都可能影响均值；不据此承诺整款游戏提升相同比例，更没有达到 25/30 FPS。整轮显示耗时包含启动、加载和截图外围时间，不能把它当作采样窗口的单帧剖析。新版本的地图采样未见先前的背景缺块；所有退出均 `rc=0`、PSRAM `delta=0`、`scale_mismatch=0`。

同时暴露出一个后续热点：取消整帧扫描后，整轮 VM 调度由 13772 次升至 1455608 次，输入轮询累计由 3.97 s 升至 12.37 s。它说明等待期间有大量空转，绝不能把日志中的 13360.8 “VM fps”视为游戏 FPS。代码中空主线程仍可被计作已运行，uncapped pacer 则只调用宿主 idle；需要进一步区分活跃 Java 计算、Object.wait/Timer 截止时间与真正空闲，再决定等待和轮询节奏。本轮没有修改这一组通用调度语义，以免影响构造期嵌套调用、输入和定时器兼容性。

## 合金弹头4第一关

`metal-play-after.json` 的末帧确认进入第一关森林实战，角色持枪，保持数字 5；240×320、MAX SIZE、JIT 关闭、音频询问选择取消，预热后采样 16 次，采样期间不截图。平均 **6.938 FPS**、中位数 **5.5**、范围 **3.6–14.6**。退出 `rc=0`、PSRAM `delta=0`、`scale_mismatch=0`。

其 `at` 类虽然继承 GameCanvas，本次运行的 `DISPLAY_IDLE skipped=0`，没有进入主动 flush 所有权分支。本优化因此不能改善它的这条提交路径。整轮约 139 秒中显示累计 37.02 秒，包含启动、导航、关卡加载，不能当作实战逐帧剖析。需要继续定位它的原生绘图、Java 计算与提交成本。

早先 `metal-level-before.json` 停在角色选择，`metal-play-before.json` 停在开场提示，均排除。后者某次冷启动还出现 132 B 宿主 PSRAM 差值；重复后及本次有效运行恢复为 0，但不据此宣称所有冷启动分配都已定位。本轮没有得到合金弹头4的有效前后配对，也没有得到两款游戏的同场景 JIT 开/关配对，因此上述 6.938 FPS 只是当前实战基线。

## nano_j2me 后续优先级

1. **分别测 Java 与原生热点。** 记录每帧 Java 执行、绘图、提交、等待和 GC；使用采样或可关闭计数，避免每个 opcode 都读计时器。当前聚合字节码数与 native 次数还不能指出具体慢函数。
2. **扩大有效的执行片段。** 现有 RV32 JIT 已有寄存器缓存、热度和代码预算；下一步应记录热点片段为什么退出、回解释器的频度，再考虑覆盖常见字段/数组访问或连接基本块。现有 CP/字段/方法缓存和融合指令已经存在，重复实现同类缓存没有意义。
3. **按真实精灵负载优化图形。** 继续比较 RGB565/ARGB8888、透明/不透明、旋转/镜像、整行与局部 blit；优先减少每像素判断和复制。可研究不可变图片的有界 RGB565/透明区缓存，必须保留 ARGB 原图以支持 `getRGB`，也不能缓存仍会被修改的图像。
4. **让普通 Canvas 有可靠的变更标记。** 普通 Canvas 可能保留 Graphics 并在 paint 返回后继续画，当前不能直接套用 GameCanvas 的 idle 判断。需要追踪全部写入路径、图像别名及视频覆盖，再按实际变更提交；漏记会导致画面冻结。
5. **安装期预处理与更紧凑的数据。** 参考 AOT/指令特化论文，评估预解析常量池、可验证的热点信息和更紧凑的宿主元数据。收益必须用相同 JAR、同场景和内存回收检查确认。

这些属于基于源码和资料的工程判断，不是已获得的性能提升。双核与 PPA 主要帮助原生绘图、显示和音频，不能直接让单线程 Java 游戏逻辑并行执行。

## VM 怎样运行，为什么 JIT 可能更慢

JAR 中的 class 被加载、解析后，由 VM 创建类、对象和 Java 线程。当前 ESP32 构建关闭 computed-goto 与融合指令，默认使用放在 IRAM 中的 switch 解释器。每次读取一个 opcode，操作局部变量/操作数栈，处理数组、字段、分支或调用；Java 线程在约 20,000 条解释指令的调度量子边界让出。这里的 Java 线程由 VM 调度，不等于各自拥有一个 ESP32 核心。

图形、媒体等 Java API 通常进入原生 C 函数。游戏线程完成绘制后提交；主循环还处理输入、重绘请求、媒体和显示。部分原生绘图及音频工作交给 Core 1。游戏线程尚未 flush 时，调度继续运行也不表示新的一张地图已经完成。

当前 JIT 是 RV32 基线块编译器：统计热点，将支持的字节码片段编译为机器码；编译器有整数/字段/数组快路径、寄存器缓存和部分循环支持。片段离开支持范围或到预算边界后回到解释器。它没有因此把 C 光栅器、LCD 等待或媒体解码一起优化。

需要分别核算探测/查表、编译/发布、机器码执行和回退成本。小片段、方法跳转频繁或编译结果反复被替换，都可能令总成本上升。现有映射模式用 256 KiB PSRAM 代码池，解释器则在内部 IRAM；缓存与外部内存竞争也是候选因素，需要测量，不能单凭存放位置认定减速原因。另有 32 KiB 内部可执行内存模式可做对照，但容量小且会挤占驱动内存。

历史 [c6b1595 实机对照](JIT_C6B1595.md) 已出现“纯计算加速、真实场景变慢”：局部变量内核 139.5→12 ms，分支内核 202→122.5 ms；固定 CPU 任务 8.60→7.89 s，而指定蹦球场景 15.33→10.62 FPS。该旧版缓存参数比当前小，不能把其中的驱逐数量直接套用到现在，但足以说明只报告内核倍数不能证明游戏加速。

优先方向是让少量真正昂贵且常执行的循环长期受益，减少探测和往返，依据当前场景的实际收益选择执行方式；不建议直接全局默认开启 JIT。
